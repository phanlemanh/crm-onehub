====================================================================================================
Data model, lifecycle and permission model for an approval-gated, AI-drafted wiki on Postgres: production precedents and ACL inheritance for derived pages
--- SUMMARY
No single mature system combines approval-gated AI proposals, per-page ACLs and an explicit rule for derived pages, so the build spec has to be composed from partial precedents. Schema-level precedents that are worth copying: MediaWiki FlaggedRevs and Approved Revs (an approved pointer kept separate from the latest revision), Outline (a base-revision precondition inside a SELECT ... FOR UPDATE predicate), Docmost (page-level restricted ACL evaluated live over ancestors, with backlinks filtered by viewer, plus multi-verifier tables), vouch (proposed/decided objects, sha256 source ids, evidence quotes, approver different from proposer), llm-wiki-compiler (approval pinned to a draft content hash), and Cortex (deterministic quote verification). On derived-page visibility the field genuinely disagrees. Microsoft documents label inheritance (the highest-priority label of the sources used, which the user may override) but not ACL inheritance. Google's and Glean's pages that I could reach say nothing about derived content. Notion states that Custom Agents can expose data to users who cannot see it directly. The Collaborative Memory paper proposes that a derived fragment is readable only if the reader can access every contributing resource, checked at read time. stigmergy, the only open-source LLM-wiki with ACLs I found, enforces write-time containment: a page's audience must be a subset of every source it used, and restricted material goes to a companion page instead of narrowing an open page. My recommendation, which is inference built on those precedents, is a ceiling rule. The default audience of a derived page is the intersection of its cited sources' audiences and is re-evaluated at read time. Widening requires a per-source declassification approval by someone who governs that source. Tightening a source hides dependents immediately and queues re-review. Deleting a source tombstones it, flags dependents, and is blocked by a legal hold. At the database level the agent should never hold a SQL connection. The API should read through a dedicated non-owner role, an approved-only view schema, a transaction-local viewer setting and RLS as a second lock, all with adversarial tests, because Prisma's own RLS extension is marked example-only and Postgres documents several RLS side channels. Research limits: the WebSearch budget (200/200) ran out early, so I read sources by direct URL, GitHub clones and the GitHub API only. Confluence approvals, Glean's citation filtering, Google Drive labels with Gemini, and the Prisma 7 transaction-context status remain unverified.
--- TENSIONS
 * Derived-content rule: Collaborative Memory checks the intersection of all contributing resources at read time (dynamic, hides broad pages when one source is narrow); stigmergy enforces a static write-time subset invariant and works around it with companion pages; Microsoft inherits only a classification label (highest priority) and lets the user override it, with no ACL derivation; Google and Glean documentation reachable here is silent. There is no settled industry rule.
 * Agent identity: Notion AI (answers as the user) versus Notion Custom Agents (own permissions, may expose data the user cannot open); Glean's agent policies can only restrict below the user's permissions. Microsoft Channel Agent does not check every channel member's permissions, which Microsoft documents as a risk.
 * Approval semantics: vouch's spec says proposals only create and approval is once-only, yet its code has an update_existing path with no base-revision check; stigmergy has no human approval at all; FlaggedRevs and Approved Revs have approval but no proposal object; Outline and MediaWiki have base-revision preconditions but no approval gate.
 * Where to store ACL truth: live recursive evaluation (Docmost) versus cached joint table (BookStack) versus materialized child copies (Outline) versus external ReBAC (SpiceDB/OpenFGA). Live evaluation avoids staleness but costs CPU; the caches have documented staleness bugs or vendor-documented lag (Glean up to 28 days).
 * Filtering placement: stigmergy pre-filters in SQL before ranking and caps; Docmost post-filters after search; WeKnora's tests show post-filtering starves results. Post-filtering can also leak counts.
 * RLS in Prisma: Postgres and Supabase promote RLS as the DB-level lock, but Prisma's only RLS reference is example-only and warns that explicit transactions may break; many production wikis (MediaWiki) instead say read-restriction extensions cannot give real secrecy and recommend separate instances.
 * Deletion versus provenance: llmwiki snapshots titles into events to keep history after delete (good for audit, bad for restricted titles); stigmergy keeps ids and hashes only; MediaWiki keeps the row but hides text; retention and legal hold argue for keeping data while privacy argues for purging.
--- IMPLICATIONS
 > Adopt the ceiling rule: derived audience defaults to the intersection of cited sources' audiences, is re-checked at proposal, approval, source-ACL change and every read, and widening needs a per-source declassification approval by a party who governs that source.
 > Prefer splitting over narrowing: the agent should propose a restricted companion page when a narrow source would shrink a broad page (stigmergy), so current readers do not lose knowledge.
 > Model the pointers exactly as FlaggedRevs/Approved Revs do: pages.approved_revision_id (what readers and the agent see) separate from head_revision_id, with a revision_seq precondition and a composite FK so the pointer cannot leave the page.
 > Approve with a compare-and-set update plus a seen_diff_sha256 check (Outline lastRevision under FOR UPDATE, llm-wiki-compiler hash pin, MediaWiki baserevid); on mismatch mark the proposal stale and re-draft rather than auto-merge.
 > Store claims and citations with quote, prefix, suffix, sha256 and a pinned source_version, and run a deterministic block-scoped, fail-closed quote verifier (Cortex verify.ts) before a proposal can be approved; require at least one citation per claim (vouch).
 > Keep one visibility predicate (a single SQL function) for pages, search, snippets, backlinks, graph, citations, diffs, audit and exports; pre-filter in SQL, never post-filter (stigmergy vs Docmost/WeKnora).
 > Do not make source sha256 globally unique across audiences and return identical 404s for hidden and missing objects; log ids and hashes rather than titles; give history and diffs only to owners, deputies, cleared approvers and auditors.
 > The approver must be able to read every source cited in the diff; otherwise route to a cleared deputy. Model owners with deputies and an ownerless state (Docmost verifiers, Notion editor rule).
 > At this scale use plain Postgres tables with flat groups (no SpiceDB/OpenFGA). Use a non-owner reader role, an approved-only view schema and a transaction-local viewer setting, with RLS as a backstop, and test it against the Neon pooler.
 > The agent should never receive SQL access; retrieval goes through API tools that take the asker's viewer id from the session. Strip external URLs and images from agent output, and never cache viewer-dependent answers across users.
 > Define source deletion as tombstone plus needs_review with a legal_hold flag that blocks purge; define rollback as a new revision plus an approvals row, with soft or hard treatment of dependents depending on the reason.
 > Add per-page agent_readable (Glean-style exclude from LLM) so a human-visible page can be withheld from the agent, for example after an erroneous rollback.
