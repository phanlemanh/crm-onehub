====================================================================================================
Enterprise and production operations of an agent-maintained (LLM Wiki) knowledge base: access control, permission-safe retrieval, audit, retention, cost, prompt injection, data residency, evaluation, and real incidents
--- SUMMARY
The Karpathy LLM Wiki gist (April 2026) describes three layers (immutable raw sources, an LLM-written markdown wiki, a schema) and works at roughly 100 sources and a few hundred pages. It has no permission, audit or multi-user model, and every enterprise write-up I found says so, though several of those write-ups come from vendors selling an alternative. The open-source implementations I read (llmwiki, llm_wiki, llm-wiki-compiler, karpathy-llm-wiki, nvk/llm-wiki) add real cost and review controls: content hashing, review queues, provenance frontmatter, lint. None of them implements per-page ACLs or ACL inheritance for LLM-derived pages. The incident record from 2024-2026 (Slack AI, EchoLeak, ForcedLeak, GeminiJack, ServiceNow, the Copilot DLP bug, Meta's Sev-1) shows three recurring failure shapes: untrusted text reaching an agent that holds a trusted user's privileges, exfiltration through auto-fetched URLs or images, and control-plane bugs where the permission or DLP layer sat inside the same product as the agent. In most of these the model did not bypass permissions; it faithfully used the victim's legitimate access. Defences that depend on the model recognising an attack are weak: the Framing Gap paper found reframed attacks succeeded 100% against a model that resisted overt ones. Defences that constrain destinations or capabilities held (0% success in that paper). Cost is modest per ingest: my arithmetic on one blogger's 35K-token estimate gives about $0.11 on Sonnet 5 at $2/$10 per MTok. The real cost risk is unbounded loops and lint passes, not a single ingest. Residency is the hard constraint for Vietnam: Anthropic's first-party API offers only 'us' or 'global' inference; Bedrock has APAC regions but no Vietnam region, and Singapore and Jakarta list only global endpoints in that table. Decree 356/2025 (effective 1 Jan 2026) treats overseas cloud processing of personal data as a cross-border transfer needing an impact-assessment dossier. Anthropic's newest 'Covered Models' also require 30-day retention and cannot run under zero data retention. Evaluation guidance converges on separate checks for retrieval, citation support and permission leakage. Provider-guaranteed citation pointers do not prove the cited text supports the claim, and one paper reports up to 57% of citations are not faithful. Human diff review is the central control in the OneHub design, and there is evidence that approval fatigue erodes such controls (users approve 93% of Claude Code permission prompts), so the diff UI and the number of pages a reviewer must approve are security-relevant.
--- TENSIONS
 * Wiki as compiled truth versus wiki as regenerable cache. Falconer-style framing has a page owner accepting drafted updates as the system of record; Proudfrog says treat the wiki as a rebuildable cache over immutable sources and avoid it where people act on it as ground truth. This decides whether an approved page or its sources is authoritative for legal hold and deletion.
 * Human approval as the main control versus approval fatigue. The design leans on a page owner approving diffs, but Anthropic reports 93% approval of permission prompts and GitHub warns reviewers feel better approving agent output. Evidence is from code and tool permissions, not wiki review, so nobody has measured this for wikis.
 * Where to enforce permissions. Tianpan argues the vector layer must enforce it so the model never sees restricted text; Truto argues metadata alone fails and wants pre-filter plus an FGA post-check with over-fetch; pgvector's README shows database-side filtering trades recall for safety. Both blogs have an interest in their own products.
 * Model-based injection defence versus architectural constraint. Anthropic and Microsoft report low attack success rates (about 1% in an adaptive test; under 2% with Spotlighting), while Willison calls a 95%-style guardrail a failing grade and the Framing Gap paper found reframed attacks at 100% against a model that resisted overt ones. Only destination allow-lists and planner/reader separation held at 0%.
 * Is 'the permissions were already wrong' a defence? Microsoft-adjacent commentary (Petri) says Copilot did not overshare, permissions did; Slack initially called cross-channel retrieval intended; but CW1226324 and GeminiJack show real control-layer or design failures, and GeminiJack involved no permission bypass at all. Fixing permissions is necessary but did not prevent these incidents.
 * Citation design. atomicstrata/llm-wiki-compiler persists source file and line-range citations and lints them; Astro-Han/karpathy-llm-wiki rejects them because agents skip the annotation rule. Separately, provider-guaranteed citation pointers do not establish faithfulness (up to 57% post-rationalised).
 * Scale. Karpathy's own figure and skeptics say a few hundred pages; Epsilla and Falconer talk about millions of documents but are vendors of alternatives; Astro-Han says add vector search only when recall measurably degrades; Truto and Tianpan assume vector retrieval from the start.
 * Cost saving versus privacy. Batch (50% off) is not ZDR-eligible and the newest Covered Models cannot run under ZDR, so the cheapest and most capable options are also the ones that retain data longest. US-only inference adds 1.1x and Bedrock regional endpoints 10%, and neither gives Vietnam residency.
 * Vietnamese cross-border rules are read differently. Rajah & Tann and Vietnam Briefing say the assessment dossier is due within 60 days of transfer and overseas cloud counts; EY's summary describes a 45-day process and says the decree does not explicitly settle overseas cloud on its own. A draft data-security law due in October 2026 could tighten this.
--- IMPLICATIONS
 > Enforce visibility below the agent, in the deterministic layer (API and Postgres), using the asking employee's identity on every agent tool call. Never put the rule in a prompt or in page text. This matches the repo rule that intelligence lives in apps/agent while the API stays deterministic. Treat Postgres RLS as a second layer (limited DB role, FORCE ROW LEVEL SECURITY, default-deny), not the only one. (inference from the RLS, pgvector, EchoLeak and Slack findings)
 > Treat every wiki surface as a leak channel, not just page bodies. Page titles, index.md, backlinks, search snippets, log.md, diff previews and citation labels can all reveal that a restricted page exists or what it says. Build the index and search results per user from the permission-filtered set rather than filtering a global index afterwards. (inference; no source tested this for wikis specifically)
 > Define a rule for derived pages before building ingest. A page synthesised from several sources should default to the most restrictive source visibility, store its source list in a database table (not only frontmatter), and require an explicit owner 'declassify' action to publish a summary of restricted material more widely. The research is thin here (Collaborative Memory only), so expect to design and test this yourselves. (inference)
 > Break the lethal trifecta by splitting the two agents. The ingest agent reads untrusted documents, so it should have no network egress and only write draft revisions. The Q&A agent should be read-only on approved revisions, with no outbound URLs or images beyond an allow-list, and no ability to read raw unreviewed uploads. Every incident above exfiltrated through auto-fetched links or images. ForcedLeak shows the CRM lead-intake endpoint is the same shape of risk if lead text ever reaches an agent. (inference from Willison, Framing Gap, EchoLeak, ForcedLeak)
 > Assume approved pages are still hostile-influenced. Second-order injection (ServiceNow) and oracle poisoning mean a hidden instruction in a source can survive into an approved page, and models trust wiki content almost fully. Make the reviewer diff show source provenance and flag imperative or addressed-to-the-AI text, mark page text as data rather than instructions in the Q&A prompt, and keep permission and role labels in database columns the model never reads as authority (DACSI). (inference)
 > Design the approval screen as a security control. Limit how many pages one ingest may change, show only the changed claims with their source spans, bind approval to the exact base revision (the plan-hash idea in nvk/llm-wiki), and run an automated check first (citation support, new-URL detection, contradiction against approved pages). The 93% approval rate for permission prompts is the warning about a screen that just asks 'OK?'. (inference)
 > Log both paths. For ingest: source hash, model and prompt version, produced diff, reviewer, decision, base revision. For Q&A: asking user, retrieved and denied page-revision IDs, model and version, token counts, answer and citation IDs, and injection or link-blocking flags. Use Microsoft's audit record as a field checklist. Keep the log append-only and outside the wiki tables; do not rely on the model provider for request logs (Anthropic API has no per-request audit feed for you). (inference plus Microsoft docs)
 > Handle retention and legal hold in your own data model. Keep raw sources immutable with hashes, keep every approved page revision immutable, add a legal-hold flag that blocks source deletion and page purge, and use tombstones with a purge job. Personal-data deletion requests have a 20-day completion window under Decree 356 (per a law-firm summary), so plan how a deleted source triggers re-review or regeneration of the pages derived from it (frontmatter or table lineage makes this possible, as in nashsu/llm_wiki). Confirm the record-retention duties for real-estate and finance documents with counsel. (inference)
 > Tier the models by task and budget every run. Use a small model (Haiku 4.5 at $1/$5) for triage and classification, a mid model (Sonnet 5 at $2/$10) for drafting, and a top model only for flagged contradiction checks. Skip unchanged sources by content hash, cache the stable schema and index prefix (reads cost 0.1x), show an estimated cost before ingest, and cap tokens per ingest and per month. The existing practice of a separate model key with a hard cap (from project memory) should be repeated for the wiki. Batch saves 50% but is not ZDR-eligible. (inference on top of verified prices)
 > Decide residency by page class, not globally. The Anthropic first-party API can pin to the US or run global; nothing pins to Vietnam or Southeast Asia, and on Bedrock only Tokyo and Melbourne pin in-region. Under Decree 356 any personal data sent overseas needs a transfer dossier, and meeting minutes and HR or customer content often contain it. Practical options: (a) keep regulations and SOPs with no personal data on a hosted model, (b) strip or pseudonymise personal data before ingest, (c) mark restricted pages 'no external model' and use a self-hosted or local-cloud model for them. Get legal sign-off before the first restricted document is ingested. (inference)
 > Choose the model tier with retention in mind. The newest Covered Models require 30-day provider retention and cannot run under ZDR, and Batch is not ZDR-eligible. If sensitive pages must run under ZDR, pin those workloads to non-Covered models and test that a 400 error from a retention mismatch fails closed rather than falling back to another provider. (inference)
 > Build the evaluation set before the first real ingest. Include: (1) permission-leak tests per role using canary strings planted in restricted pages, deterministic and run in CI on every change to prompts, models, retrieval or ACL code; (2) a golden question set (start 100-200) with expected source pages; (3) a citation-support check that the cited passage entails each sentence, since API-valid pointers and faithful citations are different things; (4) an injection corpus of hostile documents for the ingest path and hostile lead-form text; (5) retrieval recall measured separately from answer quality. (inference on top of Promptfoo, Wallat et al. and Anthropic Citations docs)
 > Keep scope small first. The reference pattern is about 100 sources and hundreds of pages and needs no vector search; one implementation says to add vectors only when recall measurably degrades. A first release with few departments, the existing role model mapped to a small number of visibility tiers (including the limited-role staff who must see no sensitive pages), and human approval on every change is defensible. Wait for measured data before widening. (inference)
 > Fail-safe behaviour for wrong answers: the company owns what its KB agent says (Air Canada). Show the page revision and its approval date in every answer, refuse to answer when retrieval finds no permitted page, and let staff flag an answer straight to the page owner. (inference)
