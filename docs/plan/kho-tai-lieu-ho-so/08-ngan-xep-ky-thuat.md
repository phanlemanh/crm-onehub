====================================================================================================
Concrete technical stack choices for a Next.js + React + Postgres LLM-wiki (Kho tai lieu): renderers, wikilink/callout plugins, editors and markdown round-trip, graph libraries, prose diff, PDF/DOCX extraction, Vietnamese Postgres full-text search
--- SUMMARY
The repo's proto/kho-tai-lieu branch already ships a reader built on Streamdown 2.6.0 with an in-house ~40-line remark wikilink plugin and a GitHub-alert callout marker, so the stack question is mostly about what to keep, harden and add. Renderers: Streamdown (Apache-2.0, unified-based) costs ~156 KB gzip in my esbuild measurement versus ~40 KB for react-markdown; the weight is parse5 from rehype-raw. Its defaults are permissive, and with default link safety every link renders as a button rather than an anchor, so the existing reader is right to disable it and override `a`. MDX is unsuitable for LLM-drafted or untrusted content because its own docs call it a programming language. The most consequential editor finding comes from my headless round-trip test on a 25-line Vietnamese wiki page: every WYSIWYG path rewrites lines. Tiptap changed 15 lines and silently dropped an HTML comment, Milkdown 9, BlockNote 12, and stock remark-stringify 7. All of them escape `[!NOTE]` and most escape `[[wikilinks]]` unless taught custom syntax; only a source editor (CodeMirror 6) is identity-preserving, which matters because reviewers approve diffs. Graphs: d3-force with SVG is enough for 50-500 nodes (layout 315 ms for 500 nodes; 60 fps at 500 nodes even under 4x CPU throttle in headless Chrome), with Quartz as a real-world precedent; Sigma/Cytoscape/vis-network are heavier than needed. Diff: jsdiff diffWords is best for prose but needs NFC normalization (mixed NFC/NFD flags every accented word), a timeout, and a block-level pre-pass because a full rewrite of 15k words took 18 s. Extraction: unpdf/pdf-parse give flat text, LiteParse recovered headings and a table locally, mammoth needs styled DOCX, and cloud parsers (Azure Layout, Google Document AI, LlamaParse) give layout-aware Markdown at roughly $1.25-$56 per 1,000 pages. Postgres: unaccent plus a custom simple-based text search configuration works for Vietnamese (verified on PG 16 and 17); phrase queries are needed because tokens are syllables; and ParadeDB pg_search was removed from Neon on 2026-09-21, which is where OneHub's production database lives. Web search quota ran out during the session, so later checks used WebFetch, the GitHub and npm APIs, and direct experiments.
--- TENSIONS
 * Bundle size versus features: react-markdown is ~40 KB gzip versus Streamdown ~156 KB, but Streamdown is already in the app for chat, gives static/streaming modes and hardening, and using two renderers risks visual drift; /packages/ui is meant to be the single UI source.
 * Streamdown's permissive defaults (all links, all images, all protocols) conflict with its own security page's warning about prompt-injected content; react-markdown's default is stricter (raw HTML shown as text, no rehype-raw).
 * Streamdown's default link safety is a security feature (confirmation modal) but produces buttons instead of anchors, which hurts keyboard, middle-click and screen-reader link semantics; a wiki needs real anchors, so the security feature must be turned off and replaced by allowlists.
 * WYSIWYG editing versus reviewable diffs: staff want Notion-like editing, but every tested editor rewrote lines, and the human approves a diff. Lexical's near-identity result comes from not understanding tables, footnotes and wikilinks (they stay as literal text), so 'faithful' and 'rich' pull in opposite directions.
 * Tiptap's docs call its markdown extension an early release while GitHub shows 2026 round-trip bugs; Milkdown is more markdown-native but has open serialization bugs; BlockNote states outright that markdown is lossy.
 * Obsidian versus GitHub callouts: Obsidian aliases `important` to tip and `caution` to warning, GitHub treats them as separate types, and GitHub forbids nesting while Obsidian allows it and adds folding; the two syntaxes cannot be treated as one without a mapping decision.
 * Wikilink pipe alias versus GFM table pipe: `[[a|b]]` inside tables must be escaped as `\|` (same as Obsidian), so agent output must follow that rule.
 * Graph library advice conflicts: Sigma's README targets thousands of nodes and its home page suggests D3 for hundreds; React Flow has the best accessibility documentation but is a node editor with a paid force layout and a Pro-only attribution removal; my benchmark shows plain SVG d3-force is adequate at 500 nodes, though only on a fast machine (degrades at 4x throttle around 500-1000).
 * diff-match-patch (archived, character-level) versus jsdiff (word-level): DMP is time-bounded and good for micro-edits, but split digits like 12 to 10 mid-number; jsdiff reads better for prose but is unbounded on rewrites unless you pass a timeout.
 * Local versus cloud parsing: LiteParse and Docling keep documents in-house but add native binaries or a Python service; Azure, Google and LlamaParse give better layout on scanned or complex files but send policy documents to a third party. LiteParse's own benchmark numbers are vendor-run, and its README recommends LlamaParse for hard cases.
 * Search engine choice: ParadeDB pg_search was a BM25 option but Neon dropped it; Neon now promotes lakebase_text (0.1.x, Databricks) while the docs also recommend plain tsvector; the LLM Wiki gist argues an index page can replace RAG infrastructure at this scale.
 * Foundation risk: CodeMirror and ProseMirror moved to a self-hosted forge (GitHub archived April 2026) while npm publishing continues, and several consumers (Tiptap, Milkdown, BlockNote) sit on that single foundation; the unified ecosystem's slow release cadence (remark-parse Sep 2023, remark-gfm Feb 2025) looks stale by dates but the repos are active.
--- IMPLICATIONS
 > Keep Streamdown as the single renderer (it is already in packages/ui and used for chat) and treat the reader's overrides as mandatory, not optional: mode=static, controls=false, linkSafety disabled with a custom `a` (real anchors), and add rehype-harden allowlists for image and link prefixes because agent-drafted pages come from untrusted source documents. If page-load weight becomes a concern, the alternative is react-markdown MarkdownAsync on the server (~40 KB gzip client cost avoided), at the price of a second renderer that can drift visually (inference).
 > Do not adopt @flowershow/remark-wiki-link 4.0.0 (broken tarball) or depend on stale packages; either keep the in-house text-node plugin or move wikilinks into an mdast node with remark-wiki-link 2.0.1 semantics so that parse and serialize share one definition. Add support for `[[Page#Heading]]`, and define a slug function with the existing Vietnamese-aware NFD/d-stroke logic plus duplicate-heading de-duplication.
 > Store canonical markdown text per revision in Postgres and derive everything else from it: rendered HTML (cached per immutable revision), a link table extracted from mdast at write time for backlinks and the graph, and the tsvector column. Normalise to NFC on ingest so diff, search and slugs behave consistently (inference built on the NFC/NFD test).
 > Author with a source editor first: CodeMirror 6 with @lezer/markdown (GFM extension, ~105 KB gzip), a wikilink and callout Lezer extension, `[[` autocomplete via @codemirror/autocomplete, and the existing renderer as live preview. It is the only option that guarantees the reviewed diff equals what the human typed and is the only one with documented no-keyboard-trap and screen-reader behaviour. Bind Tab only with a documented Escape-then-Tab hatch.
 > If staff need WYSIWYG, budget for a canonical formatter: run every revision (human or agent) through one remark pipeline with fixed stringify options plus custom handlers for wikilinks and alerts so diffs are consistently canonical. Expect a one-off normalisation diff on first save, and note the pipeline still renumbers `1. 1. 1.` lists and restyles tables (inference). Milkdown is the most markdown-native candidate; Tiptap's markdown extension dropped an HTML comment silently; BlockNote is documented lossy and has GPL/proprietary XL packages including AI.
 > Before picking any contenteditable editor, run an IME acceptance test with Telex and VNI (Unikey/EVKey on Windows, macOS Vietnamese input) covering Enter during composition, slash menus and length limits; two Vietnamese-specific bugs already exist in BlockNote and MDXEditor.
 > Diff reviewer: build on jsdiff diffWords (BSD-3) with a block-level pre-pass (paragraph or section alignment first, word diff inside matched blocks), a `timeout` fallback to line diff, NFC normalisation, and a toggle between rendered ('rich') and source diff like GitHub. No maintained markdown-structural diff package exists, so this is in-house work; react-diff-viewer-continued can render the source view. Ask the agent to write one paragraph per line, without hard wraps, so line diffs are meaningful (inference).
 > Graph: implement d3-force + SVG (about 21 KB gzip with zoom and drag) with focusable nodes as real links, compute the layout server-side or in a worker (315 ms for 500 nodes, deterministic) and cache it per link-graph version, show a local (1-hop) graph on each page and an optional global graph as Quartz does, and always provide a backlink/outlink list as the accessible alternative. Consider canvas only above ~1000 nodes; avoid React Flow unless node editing is required (Pro attribution policy, paid force layout).
 > Source ingestion: pick per file type rather than one tool. DOCX via mammoth to HTML to turndown (only reliable when Word styles are used; add an empty-header-row fix); born-digital PDF via unpdf for cheap text, or LiteParse if headings and tables must be recovered locally (native binaries, LibreOffice for Office files); scanned or complex layouts via a layout-aware service (Azure Layout, Google Document AI, LlamaParse, or a self-hosted Docling service). Pin a single pdfjs-dist version in the monorepo because pdf-parse fails on a worker version mismatch, and never expose mammoth output unsanitised.
 > Sending internal policies to a third-party parser is a data-handling decision for the owner, not a purely technical one; at a few hundred pages the cost is negligible ($1.25 to $56 per 1,000 pages for LlamaParse tiers, $1.50 to $10 per 1,000 for Google), so the choice should be driven by Vietnamese quality and data policy (inference).
 > Search: add a migration that creates the unaccent and pg_trgm extensions, the vi_unaccent configuration, a generated weighted tsvector column with a GIN index, and an IMMUTABLE f_unaccent wrapper for a trigram index on titles; query through $queryRaw with websearch_to_tsquery, quoted phrases for exact terms and ts_headline for snippets; sort titles with COLLATE "vi-x-icu". Expose it to the agent as a `search_wiki` tool next to a generated index page, and keep pgvector for later.
 > Do not plan around pg_search on Neon (removed 2026-09-21). If BM25 ever becomes necessary, lakebase_text works on ordinary tsvector columns but is version 0.1.x with VACUUM-dependent statistics; at hundreds of pages built-in ts_rank_cd is likely sufficient (inference).
 > Fix the shared callout accessibility before shipping: the reader renders callouts with the shared Alert component (role=alert), which is a live region; a static note is better served by role=note or no role, and callout type labels should be localised (the prototype already passes labels). Decide explicitly whether Obsidian aliases (important=tip, caution=warning) or GitHub's five distinct types are the house rule.
--- OPEN
 ? WebSearch quota (200 per session) was exhausted mid-research, so later coverage relied on WebFetch, the GitHub and npm APIs, and experiments; some popularity or usage claims were not cross-checked by independent search.
 ? Legacy Vietnamese PDF font encodings (TCVN3, VNI) and scanned PDFs were not tested; only a Chrome-generated born-digital PDF and two synthetic DOCX files were used, so extraction quality on real OneHub regulations is unknown. No OCR engine was run on Vietnamese scans.
 ? Azure Document Intelligence per-page prices could not be retrieved (pricing page rendered placeholders) and LlamaParse Vietnamese OCR support is not documented on the pages fetched; Google's Vietnamese listing is on the general languages page, not tied to a specific processor.
 ? Screen-reader behaviour (NVDA, JAWS, VoiceOver) was not tested for Streamdown output, callouts, SVG graph nodes or any editor; a11y statements are from docs and markup inspection only. No WCAG statements were found for Tiptap, Milkdown or BlockNote.
 ? Vietnamese IME behaviour of CodeMirror 6, Tiptap, Milkdown and Lexical was not tested; the absence of issues found is weak evidence.
 ? Round-trip results use stock configurations in jsdom with one sample document; custom extensions for wikilinks and alerts (which would change results), real LLM-drafted markdown, and MDXEditor/Crepe were not exercised.
 ? Bundle sizes are esbuild measurements without CSS and without Next.js chunking or shared-chunk deduplication; the Crepe and MDXEditor figures are totals across lazy chunks, not initial load.
 ? Performance numbers come from one Apple Silicon Mac (Node 24, headless Chrome 153, rAF-capped at 60 Hz); real office laptops, Windows and mobile devices will differ, and the 4x throttle is only an approximation.
 ? Prisma ORM 8 changes were not checked (repo is on 7.9.1); Neon's lakebase_text behaviour with a custom vi_unaccent tsvector, and its maturity (0.1.3), were not tested; Neon C.UTF-8 was tested via glibc C.utf8 and PG17 builtin C.UTF-8 locally, not on Neon itself.
 ? The Vietnamese-blog source about FTS surfaced in early search (blog.tuando.me) no longer resolves, so its claims were not used; no maintained Vietnamese-specific Postgres tokenizer was found but the search was limited to GitHub and npm.
 ? Whether GitHub alert syntax should be the canonical callout syntax, and whether the LLM will reliably emit escaped pipes and valid alert markup, are product and prompt decisions not settled by this research.
 ? Milkdown's own documentation site is a single-page app that could not be fetched; claims about it rest on the repo README, issues and the local test.
