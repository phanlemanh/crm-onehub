====================================================================================================
Content pipeline and versioning for an LLM Wiki knowledge base: ingestion (PDF, Word, scans/OCR, HTML, meetings), chunking and extraction, update-vs-create decisions, entity/link/dedup handling, lint (contradiction and staleness), claim-level provenance, proposals, prose diff, approval, rollback, audit trail, and Vietnamese-language considerations
--- SUMMARY
Karpathy's gist (posted 2026-04-04; 1,128 comments by 2026-09-24) defines only the loop: immutable raw sources, an LLM-owned wiki, a schema file, and ingest/query/lint operations, with one source touching roughly 10-15 pages and git suggested as the history layer. Everything the OneHub feature needs (proposals, approval, provenance, diffs) has been invented by the ecosystem since, and the projects disagree. The clearest consensus is that model judgment should cover only content decisions (what to extract, update vs create, whether two claims conflict) while linking, citation checking, staleness detection and structural validation are deterministic code; Meta's Sept 2026 production write-up and LangChain's OpenWiki claims runtime are the strongest examples. Review-gated designs exist (llmwiki candidates with approval pinned to the exact reviewed body, swarmvault approval bundles, sage-wiki quarantine, Meta's PR plus adversarial reviewer plus regression suite), but most personal-wiki tools default to writing live, and MediaWiki's history shows over-elaborate approval schemes get abandoned (FlaggedRevs) while a simple approved-revision pointer survives (Approved Revs) with a known leak: other readers may still fetch the latest, unapproved revision. Evidence on quality is thin and mixed: a preregistered small study found wiki claims better supported by their cited excerpts than RAG claims but ~21x more tokens per query and no measurement of wiki-page-vs-source fidelity, and WiCER shows blind LLM compilation silently drops facts (53-60% failing answers vs 17% for raw context) which matters when the company agent can read only approved pages. For prose diffs the proven pattern is block alignment plus word-level inline diff with moved-paragraph detection (Wikimedia wikidiff2) and semantic cleanup of character diffs (diff-match-patch); suggestion-mode editor libraries exist but track editing steps rather than whole-page LLM rewrites. For Vietnamese, no LLM-wiki source addresses it, but general sources and my own small tests show concrete traps: NFC/NFD and old/new tone-mark placement create false diffs and break exact-quote checks, OmniDocBench has no Vietnamese, Vietnamese OCR accuracy varies enormously by model, and LLMs performed very poorly at detecting conflicts between Vietnamese legal provisions in the 2026 VietLegal benchmark. Coverage caveat: the WebSearch budget (200 calls) ran out midway, so later discovery relied on GitHub API, arXiv API and direct fetches.
--- TENSIONS
 * Auto-apply versus human approval: LLM Wiki v2 wants self-healing lint that fixes what it can and LLM-picked contradiction winners; Astro-Han auto-applies 'safe fixes'; llmwiki writes live by default and holds only risky pages; OneHub's stated model is that a human page-owner approves every change. Only mechanical, deterministic fixes are candidates for pre-approval, and even those need to appear in the audit trail.
 * Resolve versus surface contradictions: LLM Wiki v2 has the model propose a winner by recency, authority and support count; GBrain, Evenson and Astro-Han say show both claims and never silently resolve; llmwiki holds contradicted pages for review; a commenter wants write-time resolution through declared exclusive predicates rather than lint-time discovery. For Vietnamese law, models were poor at conflict detection (VietLegal), which favors surfacing plus structured amendment data.
 * Confidence scores: LLM Wiki v2, llmwiki (0.5 hold threshold) and sage-wiki (0-1, 0.85 auto-apply) use numeric confidence; Astro-Han calls it false precision with no calibration and puts evidence strength in prose.
 * Staleness mechanism: per-page timers (OKF stale_after) versus whole-wiki lint (Astro-Han rejects per-article review dates) versus evidence-version comparison (OpenWiki claims, llmwiki source hashes, Evenson timestamps). Astro-Han's simplicity relies on raw sources being immutable, which does not hold when regulations are amended and re-issued.
 * Citation granularity: none/whole-file grep (Astro-Han), line ranges (llmwiki), claim records with evidence versions (OpenWiki), source-level (GBrain), sentence-level (Anthropic Citations). Cochran's data shows claim-level checks and holistic judges diverge, and citation-faithfulness papers show attached citations can be post-rationalized.
 * Git as review layer versus purpose-built content operations: several teams use git PRs (Meta, the Rakuten-style team-wiki comment, OKF); Sanity and innobu argue non-technical approvers need documents with effective dates and sign-off records, and that git history is not compliance-grade. Both critics have commercial interests.
 * Wiki versus RAG economics: Karpathy expects cheap queries after paying ingest; Cochran measured ~21x more tokens per query and refuted break-even; Meta reports ~80% token reduction from a staged wiki design; a commenter found no saving for small greppable sources; WiCER shows compiled wikis lose facts. Results depend on corpus size, retrieval baseline, judge and what the wiki compresses.
 * Deterministic versus LLM linking and entity work: WikiLoom and GBrain keep linking model-free; sage-wiki and llmwiki use LLM-extracted relations; sage-wiki still gates entity merges behind review.
 * Approval-scheme complexity: MediaWiki abandoned FlaggedRevs' multi-dimension ratings as clunky while keeping Approved Revs' single pointer, which itself leaks to non-aware readers; Meta layers adversarial review, tests and expert sign-off. Simplicity of the human step versus depth of automated pre-checks is an open design choice.
 * Vietnamese word segmentation: PhoBERT-family models require pre-segmented text, BamiBERT and multilingual embedders do not; the only retrieval report recommending segmentation is a student project. No 2026 evidence settles it for OneHub's retrieval stack.
--- IMPLICATIONS
 > INFERENCE - Model the pipeline as proposals, never direct writes. Immutable SourceVersion (content hash, upload date, document effective date, original file kept) -> immutable PageRevision rows -> a Page row that holds only a pointer to the current approved revision. An agent-produced proposal is a PageRevision in 'pending' state with baseRevisionId, source spans and a reason. Approve = compare-and-swap of the pointer, pinned to the exact content hash the owner saw (llmwiki), and rejected if the base revision moved (a human edited meanwhile). Rollback = a new revision that copies an older one, never deletion. Record actor as agent/<model>@<prompt-version> versus human:<user id> (OKF convention) so the audit trail distinguishes who wrote from who confirmed.
 > INFERENCE - Enforce 'company agent reads approved pages only' at one retrieval choke point (a database view or single query function), because MediaWiki's Approved Revs shows other readers can bypass an approval pointer and get the latest revision. Also keep the agent's own answers out of the wiki unless they go through the same proposal path (sage-wiki quarantine lesson).
 > INFERENCE - Build a claim ledger next to each page revision: each material claim gets a statement, evidence spans (source chunk id, character offsets, verbatim quote, 32-char prefix/suffix as in W3C TextQuoteSelector), and the source version it was checked against. Run deterministic checks before a human sees a proposal: quote exists (after NFC normalization; fuzzy Bitap fallback with a threshold), numbers/dates in the page appear in cited spans, no dangling links or duplicate slugs, source version still current. Stale detection then becomes a model-free comparison of stored vs current source version (OpenWiki). This fits the repo rules: the ingestion agent lives in apps/agent, the API only stores/serves proposals and approvals, and the ledger and proposal payloads are parsed with Zod in packages/validation rather than passed as loose JSON.
 > INFERENCE - Review UI should be more than a text diff: (1) block-aligned rendered prose diff with word-level highlights inside changed paragraphs and moved-paragraph detection (wikidiff2 approach; jsdiff diffWords or diff-match-patch semantic cleanup as building blocks); (2) a machine-extracted 'facts changed' strip listing every added/removed number, percentage, date, deadline and named entity, since these are the high-risk edits in regulations and pass unnoticed inside prose; (3) side-by-side source passage with highlight (page and bounding box for PDFs, which Docling can supply); (4) flags for contradiction/supersession candidates and OCR-derived evidence; (5) per-hunk accept with owner edits, recording both proposal hash and approved hash. Cited claims were verified only for claim-to-excerpt alignment in the literature, so the reviewer, not the model, must own page-vs-source fidelity.
 > INFERENCE - Add a coverage check to compensate for silent fact loss (WiCER): after drafting, extract candidate facts from the source (numbers, obligations, deadlines, thresholds, definitions) and verify each is represented in some proposed page or explicitly marked out of scope; show unrepresented items to the owner. Because the agent can only read approved pages, a fact dropped at compile time is unrecoverable at answer time. This exposes a product decision for the owner: wiki-only answering versus wiki-first with a clearly labeled source-search fallback (Meta splits wiki and RAG by density and frequency; Cochran and WiCER show wiki-only trades recall and cost).
 > INFERENCE - For Vietnamese legal and policy sources, do not rely on the LLM to detect conflicts or amendment direction (VietLegal: 16 of 23 models scored 0.00 on conflict detection; temporal-direction confusion). Store document number, issue date, effective-from/effective-to and status as structured fields, and keep an explicit relation table (amends, replaces, repeals, guides) that humans confirm; chunk by Chuong/Dieu/Khoan/Diem with the path as the chunk key. Model two clocks: effective dates of the rule (valid time) and approval time of the page revision (belief time), so 'what did the agent tell staff on date X' is answerable. Surface conflicts to the page owner; never auto-resolve.
 > INFERENCE - Vietnamese text hygiene: normalize every stored string, quote and search key to NFC at the ingestion boundary and keep original bytes of the source file; treat hóa/hoá style tone placement as a search equivalence rather than rewriting text; keep an unaccented search column (PostgreSQL unaccent) plus trigram/full-text on the 'simple' configuration since Snowball has no Vietnamese stemmer; decide on word segmentation only if a PhoBERT-family model is chosen. Pin jsdiff >=8.0.4 if using its Intl.Segmenter path, and remember Intl.Segmenter('vi') yields syllables, so word diffs are syllable diffs (readable enough for review).
 > INFERENCE - OCR and Word intake: pick the parser by testing 30-50 of OneHub's own scans (stamps, signatures, tables, faint faxes) since OmniDocBench has no Vietnamese and CER ranged from ~4% to over 200% in VMMU; keep the scan and OCR text side by side, mark OCR-derived sources lower-trust, require the reviewer to view the source region for any number taken from OCR, and consider a second engine disagreement on numeric tokens as a review trigger. Fail loudly on empty extraction (MarkItDown's silent OCR skip), ingest .docx with tracked changes as 'all' or reject them (pandoc default silently accepts), check parser licenses (MinerU revenue thresholds, Marker weights terms; Docling MIT).
 > INFERENCE - Quality gates before the human (Meta pattern, scaled down): a deterministic linter that blocks malformed proposals; an adversarial reviewer agent in fresh context that sees only the diff and the cited spans; and a regression set of real staff questions with expected cited answers, re-run after every approved change, with each accepted correction added to the set. Keep the approval rule itself simple (one owner per page, one approved pointer) because FlaggedRevs' multi-dimensional review scheme was abandoned.
 > INFERENCE - Reduce reviewer load and fatigue: one source can trigger 10-15 page updates, so group proposals by source, add a 'no material change' disposition, risk-tier proposals (numbers, thresholds, deadlines, legal citations = high; typo or link fixes = low), and only allow pre-approved auto-apply for purely mechanical, deterministic fixes with the policy still visible in the audit log. No source measured reviewer accuracy or automation bias on LLM-proposed prose diffs, so plan to measure it in a pilot (time per proposal, defects found post-approval).
 > INFERENCE - Cost and safety controls: estimate tokens and refuse before running an ingest if it would exceed budget (WikiLoom pattern), use prompt caching, and expect wiki-style ingest to be far costlier than RAG indexing (Cochran: about 900M gross tokens vs 1.4M for 24 papers; billing-weighted 136-161M). Project notes indicate the existing agent runs under a hard AI spend cap; check current figures before designing batch ingest.
