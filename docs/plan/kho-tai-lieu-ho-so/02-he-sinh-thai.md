====================================================================================================
Ecosystem of existing LLM Wiki implementations (state of play on 2026-09-26)
--- SUMMARY
Karpathy's April 2026 gist (raw sources, LLM-written wiki, schema file; ingest/query/lint; index.md and log.md) has produced a very large but young and shallow ecosystem: 486 GitHub repos carry the llm-wiki topic, the gist has roughly 9,900 forks, the curated awesome-llm-wiki list links about 197 repos, and the Obsidian plugin directory has 20+ LLM-wiki plugins. Almost everything is under six months old and pre-1.0 or fast-churning, and several early leaders are already quiet (kytmanov's original in maintenance mode, Pratiyush since mid-June, SwarmVault since end of June). All of the ~17 implementations I read in detail share the same core: markdown pages with YAML frontmatter and [[wikilinks]], an immutable raw-source layer, ingest/query/lint operations, provider-agnostic LLM use, and an MCP server or Agent Skill for agents. They differ on the things OneHub cares about most. Only Synto (kytmanov's successor) defaults to a draft queue with human approval; atomicstrata/llm-wiki-compiler, SwarmVault, claude-obsidian and auto-llm-wiki make review opt-in; nearly everyone else (nashsu, OpenKB, GD4AI, llmwiki, Kompl, Pratiyush, wikillm) writes directly, and Stigmergy rejects approval queues on principle. Multi-user identity, roles and per-page ACLs are the biggest hole: nearly every tool is single-user by design, sage-wiki's own security document says it has no multi-user authorization model, KiwiFS lists RBAC as unshipped, and only Stigmergy (9 stars) and wikihub.md (hosted, marketing page) show per-page ACLs. The most reusable ideas are pattern-level: atomicstrata's hash-pinned approvals and policy-based holds, Synto's reject-with-feedback loop and 'drafts hidden from MCP', claude-obsidian's expected-SHA-256 transactions, sage-wiki's answer quarantine and untrusted-source prompt boundary, Stigmergy's ACL-aware writes and Postgres capture queue, and OKF v0.2's provenance/trust/lifecycle frontmatter. Real users report concrete scaling and safety failures (O(N^2) page rewrites at ~1,100 documents, truncated LLM output overwriting pages, unsanitized rendered markdown, non-Latin text tokenized to nothing). No project documents Vietnamese support, and the tokenizer bug class is directly relevant. Licences (GPL/AGPL/BSL on several of the most capable projects) mean OneHub should borrow designs, not code. Caveat: my WebSearch budget ran out mid-session, so late-stage checks relied on the GitHub API, primary READMEs/docs/issues and WebFetch.
--- TENSIONS
 * Autonomy versus review: the gist has the LLM own the wiki layer; laphilosophia and bluewater8008 argue for diffs and human verification; Stigmergy deliberately has no approval queue and relies on deterministic gates; atomicstrata built a full queue but leaves it off by default; llmwiki writes immediately. Only Synto defaults to human approval.
 * Hand edits: Synto and GD4AI protect them (hash detection, reviewed: true), claude-obsidian treats a changed target as a conflict, OpenKB overwrites them on recompile.
 * Retrieval: GD4AI rejects embeddings while nashsu, sage-wiki, atomicstrata and SwarmVault use vectors; each publishes its own benchmark, and GD4AI's own issue #480 undermines its PPR result.
 * Source of truth: files plus git (KiwiFS, inkeep, OpenKB, GD4AI) versus Postgres (llmwiki hosted, sage-wiki option, WikiBrain, Stigmergy operational state) versus hybrids with hidden DB state (Synto's gitignored state.db cannot be restored by git revert; Kompl keeps one previous version).
 * Team claims versus reality: sage-wiki's team guide says 3-50 users while its security contract says no multi-user authorization model; llmwiki README targets organisations but its schema is owner-only; KiwiFS pitches replacing Confluence while listing RBAC and co-editing as missing.
 * Scale claims versus field reports: sage-wiki claims 100K+ documents; a user reports OpenKB needing tens of hours for ~1,100 documents; a blogger reports a 150-200 page context ceiling without an index.
 * Trust scope: sage-wiki quarantines query answers to stop wrong outputs compounding, but compiled articles are written directly; atomicstrata's policy doc leaves query --save ungated; Karpathy's 'file good answers back' increases feedback-loop risk.
 * README comparison tables are biased (GD4AI's table mislabels atomicstrata as Markdown-only); popularity metrics diverge from maturity (nashsu 19,989 stars and ~132K downloads but a single-user GPL desktop app; wikillm 0 stars).
 * Who runs the LLM: tools with a built-in pipeline (nashsu, OpenKB, Synto) versus substrates driven by external agents over MCP (KiwiFS, llmwiki, inkeep); OneHub already has its own agent, which matches the second group.
 * OKF: v0.2 records verifier as human:<id> and advisory trust tiers but explicitly is not access control, while team deployments need enforced permissions.
--- IMPLICATIONS
 > Adopt patterns, not code: the closest matches to the target design are atomicstrata (candidate queue, hash pins, policy holds), Synto (default draft queue, reject-with-feedback, drafts hidden from MCP), KiwiFS (draft spaces, comments, workflows) and Stigmergy (Postgres capture queue plus ACL-aware writes); none of them is a finished fit for Vietnamese staff (inference), and licences block copying from nashsu, inkeep, KiwiFS and WikiBrain.
 > Make human approval the default for every agent write (only Synto does this) and use atomicstrata-style risk signals (low confidence, contradiction, missing citation, schema breach) to order and label the review queue rather than to skip review.
 > Each proposal must record the base page version or hash it was generated against, and approval must fail when the live page has moved (atomicstrata precondition, claude-obsidian expected SHA-256); this also answers the stale-diff concern raised in inkeep issue #1237 and maps onto optimistic locking in Prisma/Postgres.
 > Model reject as a first-class state: keep the reason, feed it to the next generation, and stop re-proposing an unchanged source (atomicstrata sticky reject plus Synto five-strike block).
 > Enforce 'agent answers only from approved pages' in the data model (a published-version pointer per page and a retrieval query that can only see published versions) rather than in prompts; Synto's hidden drafts and sage-wiki's include_outputs mode are the reference behaviours, and every answer should cite page and version.
 > Store page metadata compatible with OKF v0.2 (type, sources with stable ids and footnote citations, generated.by/at, verified as human:<id> events mapped to the page-owner approval, status, stale_after for regulation effective or expiry dates); note OKF has no owner field, so page-owner assignment and supersession links must be OneHub's own design (KiwiFS workflows and Falconer routing are the only precedents).
 > Do not treat any existing tool's identity model as sufficient: build page ownership, roles and per-page visibility into Postgres from the start (Stigmergy's acl groups and visibility-aware writes are the only serious reference), and make the ACL apply to the agent's retrieval as well.
 > Validate every LLM write deterministically before it becomes a proposal: complete-output check (truncation overwrote pages in GD4AI), required citations with a check that quoted spans exist in the source (sage-wiki edge-span rule), link resolution, and rejection of non-answers (OpenKB #225).
 > Design ingestion for topically dense regulatory corpora: avoid per-document full-page rewrites (OpenKB O(N^2)); use a plan-then-write flow (Kompl's deterministic page plan, nashsu's analysis-then-generation, OpenKB's proposed map/reduce), a durable leased queue (Stigmergy, nashsu) that fits the existing AgentTask rows, and bounded index or listing prompts.
 > Treat ingested regulations and SOPs as untrusted input for prompt injection (wrap and neutralise delimiters as in sage-wiki) and sanitise rendered markdown before display (Kompl's XSS disclosure); include page-version pins so a poisoned draft cannot silently reach the Q&A agent.
 > Test Vietnamese explicitly: run search tokenization with diacritics (both accented and unaccented queries), choose Postgres text search config or unaccent plus a multilingual embedding model, and build a small Vietnamese Q&A evaluation set; no surveyed project documents Vietnamese and one widely used tokenizer default shatters it (my regex test).
 > Include an evaluation harness from day one (citation coverage/precision as in atomicstrata eval, grounding score as in sage-wiki) because published retrieval benchmarks are self-reported and inconsistent (GD4AI 27.1% vs 24.1%; nashsu 58.2% -> 71.4%).
 > Keep staff off Obsidian and CLI tools: the Obsidian plugins and skills are single-user, so OneHub needs its own web editor and diff-review UI (reference designs: KiwiFS and nashsu UIs; OpenKnowledge's Cursor-style accept/decline is still an open request), consistent with the shared UI package rule.
